# Database Design

Status: Ready — schema and migrations remain to be implemented.

## Ownership and migrations

PostgreSQL is the sole persistent store. Flyway creates and evolves the schema through:

```text
backend/src/main/resources/db/migration/
├── V1__create_schema.sql
└── V2__seed_demo_data.sql
```

Set `spring.jpa.hibernate.ddl-auto=validate` and `spring.jpa.open-in-view=false`. Add new versioned migrations after a migration has been applied or shared. Startup must preserve user balances, sessions, and payments; it must not reseed or clear existing rows.

Use `bigint GENERATED BY DEFAULT AS IDENTITY` for primary keys, `numeric(12,2)` for money, and `timestamptz(3)` for instants. Map status enums as strings. All fields are non-null unless explicitly listed as nullable.

## Tables

### `users`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | bigint identity | Primary key |
| `name` | varchar(120) | Nonblank display name; not required to be unique |
| `balance` | numeric(12,2) | Default `0.00`; `balance >= 0` |

### `vehicles`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | bigint identity | Primary key |
| `plate_number` | varchar(32) | Nonblank, globally unique |
| `user_id` | bigint | Foreign key to `users(id)` |

Add `UNIQUE (id, user_id)` to support the composite ownership foreign key from sessions. Plates are seeded in normalized uppercase without spaces. There is no plate-entry API in this version.

### `cities`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | bigint identity | Primary key |
| `name` | varchar(120) | Nonblank, unique |

### `parking_zones`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | bigint identity | Primary key |
| `name` | varchar(120) | Nonblank |
| `city_id` | bigint | Foreign key to `cities(id)` |
| `price_per_hour` | numeric(12,2) | `price_per_hour >= 0` |
| `active` | boolean | Default `true` |

Add `UNIQUE (city_id, name)`. The same zone name can occur in different cities.

### `parking_sessions`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | bigint identity | Primary key |
| `user_id` | bigint | Foreign key to `users(id)` |
| `vehicle_id` | bigint | Vehicle ownership enforced by composite foreign key below |
| `zone_id` | bigint | Foreign key to `parking_zones(id)` |
| `hourly_rate` | numeric(12,2) | Captured at start; nonnegative and immutable |
| `started_at` | timestamptz(3) | Set by the server at start |
| `ended_at` | timestamptz(3) | Nullable while active |
| `amount` | numeric(12,2) | Nullable while active; nonnegative when present |
| `status` | varchar(16) | Only `ACTIVE` or `COMPLETED` |

Require `FOREIGN KEY (vehicle_id, user_id) REFERENCES vehicles(id, user_id)`. This protects ownership consistency as well as vehicle existence.

Require state consistency:

```sql
CHECK (
    (status = 'ACTIVE' AND ended_at IS NULL AND amount IS NULL)
    OR
    (status = 'COMPLETED' AND ended_at IS NOT NULL AND amount IS NOT NULL)
),
CHECK (ended_at IS NULL OR ended_at >= started_at),
CHECK (amount IS NULL OR amount >= 0),
CHECK (hourly_rate >= 0)
```

Require one active session per vehicle:

```sql
CREATE UNIQUE INDEX uq_parking_sessions_active_vehicle
    ON parking_sessions (vehicle_id)
    WHERE status = 'ACTIVE';
```

Completed rows do not prevent another session for the vehicle. A completed unpaid session also does not block a new session.

### `payments`

| Column | Type | Rules |
| --- | --- | --- |
| `id` | bigint identity | Primary key |
| `parking_session_id` | bigint | Unique foreign key to `parking_sessions(id)` |
| `amount` | numeric(12,2) | Nonnegative; exact copy of the final session amount |
| `status` | varchar(16) | Only `PAID` |
| `paid_at` | timestamptz(3) | Set by the server when payment succeeds |

Name the unique constraint `uq_payments_parking_session`. Payment amount equality, completed-session eligibility, and `paid_at >= ended_at` are cross-table rules enforced in the service transaction. Do not introduce database triggers for these rules in the prototype.

## Indexes and deletion behavior

Besides primary keys and unique constraints, add indexes supporting the actual access paths:

```sql
CREATE INDEX ix_vehicles_user ON vehicles (user_id);
CREATE INDEX ix_parking_sessions_user_status_start
    ON parking_sessions (user_id, status, started_at DESC, id DESC);
```

The city/name unique index supports zone lookup by city. The payment/session unique index supports joins and duplicate detection. Add further indexes only if queries justify them.

Use foreign keys with no cascading deletion. Deletion is not exposed by the API. Add nonblank checks for names and plate numbers using the equivalent of `length(btrim(column_name)) > 0`.

## Monetary limits

The largest allowed monetary value is `9999999999.99`. Validate input precision and scale before persistence; do not rely on the database to round invalid input. Top-up must reject a resulting balance above the limit with the API's documented conflict error.

If a calculated parking charge exceeds the storage limit, reject stop with `AMOUNT_LIMIT_EXCEEDED`, leaving the session active. Do not clip the charge. This is an explicit prototype storage limit; there is no administrative correction workflow in scope.

## JPA mapping expectations

- Use `BigDecimal` with precision 12 and scale 2 for money.
- Use `Instant` for all timestamps and align stored precision with the [time decision](architecture.md#time-and-pricing).
- Use lazy relationships by default, with deliberate fetch plans for DTO responses.
- A session has many-to-one relationships to user, vehicle, and zone. Payment owns the one-to-one session foreign key. A reverse session/payment mapping is optional if repositories provide the required lookup efficiently.
- Avoid cascade-remove and JSON serialization of entities.
- Database constraint names needed for error translation must match the migration definitions.

## Verification

Apply migrations to an empty PostgreSQL database, start Hibernate validation, and restart against the same database. Test the active-session index, payment uniqueness, ownership foreign key, session checks, monetary constraints, and seed sequence behavior against PostgreSQL. See the [testing strategy](testing.md).
